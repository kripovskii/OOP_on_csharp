# Часть 1. Краткий обзор оперативной памяти и её слоёв

### 1.1 Иерархия памяти (вкратце)

* **Регистры CPU** — самые быстрые, размер слов CPU (32/64 бита).
* **Кэш (L1/L2/L3)** — микропамять очень быстрая, работает построчно (cache line, обычно 64 байта).
* **Оперативная память (DRAM, RAM)** — основная оперативная память процесса.
* **Накопитель (SSD/HDD)** — гораздо медленнее; используется для подкачки (swap) и хранения.

Ключевые последствия:

* Доступ к памяти локально по адресу в кэше гораздо быстрее, чем при промахе кэша.
* Выравнивание (alignment) и размер кэш-линии влияют на производительность.
* **False sharing**: два потока модифицируют разные данные в одной кэш-строке — производительность падает.

### 1.2 Виртуальная память и страницы

* Процессу ОС предоставляет **виртуальное адресное пространство** (VA). VA мапится на физические страницы (PA) через таблицы страниц.
* **Страница** — базовая единица управления (обычно 4 KB).
* При обращении к неотражённой странице происходит **page fault** → ОС подгружает страницу из диска/подменяет и т.д.
* Виртуальная память даёт изоляцию процессов и удобство: адреса внутри процесса кажутся непрерывными.

### 1.3 Стек и куча (heap)

* **Стек (stack)**: локальные переменные, параметры, адрес возврата. Быстро (LIFO), ограничен по размеру (риск `StackOverflow`).
* **Куча (heap)**: объектная память — динамическая, управляется сборщиком (в managed-средах) или вручную (C/C++).
* Аллокация на стеке обычно — простое сдвигание указателя стека. Аллокация в куче сложнее и медленнее, требует управления свободными блоками/GC.

# Часть 2. Как устроена память в .NET / C#

### 2.1 Managed heap и сборщик мусора (GC) — основы

* .NET использует **управляемую кучу** и **сборщик мусора** (GC). Вы создаёте объекты (ссылочные типы) — они попадают в кучу, GC периодически освобождает недоступные объекты.
* **Быстрая аллокация**: для небольших объектов аллокатор обычно просто движет указатель (bump-pointer) в области для быстрой генерации (ephemeral segment) — очень быстро.
* **Generations**: объекты делятся на поколения (gen0, gen1, gen2). Идея: большинство объектов короткоживущие (очищаются в gen0). Чем старее объект — тем реже GC его проверяет.
* **Large Object Heap (LOH)**: большие объекты (приблизительно > ~85 KB исторически) выделяются отдельно; работа с LOH имеет особенности (фрагментация). Замечание: точный порог может варьироваться с реализацией runtime.
* **Компактация**: при GC живые объекты перемещаются, чтобы устранить фрагментацию; все ссылки обновляются. **Pinned**-объекты (закреплённые) мешают компактации.
* **Finalizers**: объекты с финализаторами помещаются в очередь финализации и освобождаются в две фазы — это замедляет сборку, поэтому `IDisposable` + `using` предпочтительнее.

### 2.2 Структура объекта в управляемой куче (упрощённо)

```
[ ObjectHeader | MethodTablePointer | Field1 | Field2 | ... ]
```

* **ObjectHeader** — служебные данные (например, для синхронизации, тонкая информация о состоянии).
* **MethodTablePointer** — указывает на метаданные типа (vtable-подобная структура).
* Поля следуют сразу после.

### 2.3 Жизненный цикл объекта, когда вызывается GC

* GC запускается, когда:

  * Нет свободного места для новых аллокаций в текущем сегменте.
  * Система/процесс просит явно (хотя `GC.Collect()` — плохая практика).
  * Наблюдаются условия повышенного давления памяти.
* Типы GC: background, concurrent, workstation, server — для разных сценариев (latency vs throughput).

# Часть 3. Типы в C#: value types vs reference types

### 3.1 Value types (значимые типы)

* `struct` и примитивы (`int`, `double`, `bool`) — **value types**.
* Хранятся *по значению*: если переменная — `int a = 3; int b = a;` — копия.
* Обычно располагаются в том месте, где объявлены: в стеке (локальные) или как часть полей объекта (в куче внутри объекта).
* Не требуют сборки мусора для самой «значимости», но могут быть частью объекта в куче.

### 3.2 Reference types (ссылочные типы)

* `class`, `interface`, `delegate`, `string` — **reference types**.
* Переменная содержит **ссылку** (указатель-обёртку) на объект в управляемой куче.
* Присвоение копирует ссылку, а не содержимое. `obj2 = obj1;` — теперь две ссылки указывают на один объект.
* Ссылочные типы могут быть `null` (если включены nullable reference types, поведение уточняется).

### 3.3 Boxing / Unboxing

* Преобразование value type → object (или интерфейс) называется **boxing**: выделяется объект на куче, копируется значение.
* **Unboxing** — извлечение значения из `object` обратно в value type; требует явного приведения и может бросать исключение при несоответствии типа.

```csharp
int i = 42;
object o = i;       // boxing
int j = (int)o;     // unboxing
```

# Часть 4. Ссылки в C# (reference semantics и ключевые слова)

### 4.1 Что такое «ссылка» в привычном смысле C#

* Когда мы говорим «ссылка» (reference), обычно имеем в виду ссылку на объект в куче. Эта ссылка логически похожа на указатель, но:

  * **безопасная** (managed) — GC отслеживает её,
  * нельзя выполнять арифметику адресов над ней,
  * может быть `null`.

### 4.2 `ref`, `out`, `in` — передача по ссылке

* `ref` — передаёт переменную по ссылке, вызов может прочитать и изменить исходную переменную.
* `out` — передаёт «пустой» аргумент, который должен быть инициализирован в методе (для возвращения нескольких значений).
* `in` — передаёт по ссылке, но **только для чтения** (позволяет избежать копирования больших `struct`).
  Примеры:

```csharp
void Increment(ref int x) => x++;
void Init(out int x) { x = 10; }
void ReadOnly(in MyStruct s) { /* s нельзя изменить */ }

int a = 1;
Increment(ref a); // a == 2

int b;
Init(out b); // b == 10
```

### 4.3 `ref` locals и `ref` returns (C# 7+)

* Метод может **вернуть ссылку** на элемент массива/поля: `ref int`.
* Используется для изменения элемента напрямую через ссылку, без копирования.

```csharp
static ref int Find(int[] arr, int value)
{
    for (int i = 0; i < arr.Length; i++)
        if (arr[i] == value) return ref arr[i];
    throw new InvalidOperationException();
}

// Использование:
int[] a = {1,2,3,4};
ref int r = ref Find(a, 3);
r = 99; // теперь a[2] == 99
```

### 4.4 Отличие C#-ссылки от C++-ссылки

* C# `ref` — это ссылка, которую можно переназначать (в некоторых сценариях), и она управляется GC; C++ reference — алиас, не может быть «переустановлен».
* C#-ссылки имеют правила безопасности и не допускают арифметику.

# Часть 5. Указатели в C# (`unsafe`) — что можно и зачем

### 5.1 Когда нужны указатели

* Interop с нативным кодом (P/Invoke).
* Высокопроизводительные операции с памятью (меньше проверок, копирований), манипуляции с бинарными буферами.
* Работа с оборудованием или нестандартными структурами.

**Однако**: указатели опасны — приводят к возможным ошибкам памяти (buffer overflow, use-after-free). Предпочитайте `Span<T>` / `Memory<T>` / `Marshal` / `SafeHandle` если возможно.

### 5.2 Как включить `unsafe`

* В .NET Core / SDK: добавить в csproj:

```xml
<PropertyGroup>
  <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
</PropertyGroup>
```

* Или компиляция csc: `csc /unsafe Program.cs`

### 5.3 Синтаксис: `&`, `*`, арифметика указателей

* `&var` — адрес переменной.
* `*ptr` — разыменование.
* Арифметика: `ptr + 1` сместит адрес на размер типа (`sizeof(T)`).

Пример:

```csharp
unsafe
{
    int x = 10;
    int* p = &x;
    Console.WriteLine(*p); // 10
    *p = 20;
    Console.WriteLine(x);  // 20
}
```

### 5.4 Массив и `fixed`

* Адрес на управляемый массив возможен **только** внутри `fixed`, чтобы предотвратить перемещение объекта сборщиком:

```csharp
int[] arr = {1,2,3};
unsafe
{
    fixed (int* p = arr)
    {
        // p указывает на arr[0]
        int second = *(p + 1); // 2
    } // по выходу из fixed — объект снова может быть перемещён GC
}
```

### 5.5 `stackalloc`

* Выделение памяти на стеке:

```csharp
Span<int> span = stackalloc int[128]; // безопасный способ с .NET Core
span[0] = 42;
```

Раньше `stackalloc` возвращал ненадёжный указатель, теперь чаще используется вместе со `Span<T>` (type `ref struct`, стековый).

### 5.6 IntPtr, Marshal и unmanaged memory

* `IntPtr` / `UIntPtr` — платформо-зависимые целочисленные указатели/хранители адресов.
* `Marshal.AllocHGlobal` / `Marshal.FreeHGlobal` — выделение/освобождение нативной памяти.

```csharp
IntPtr mem = Marshal.AllocHGlobal(100);
try
{
    // работа с памятью (Marshal.Copy, Marshal.WriteByte и т.д.)
}
finally
{
    Marshal.FreeHGlobal(mem);
}
```

### 5.7 Закрепление (pinning) и `GCHandle`

* `GCHandle.Alloc(obj, GCHandleType.Pinned)` — закрепляет объект в куче, чтобы GC не перемещал его. Используется при interop.
* Закрепление уменьшает эффективность GC и может вызвать фрагментацию, поэтому закрепляйте минимально.

# Часть 6. Безопасные современные альтернативы указателям

* **Span<T> / ReadOnlySpan<T>** — стек-ориентированные срезы памяти: безопасные, быстрые, не требуют `unsafe` для большинства задач.

  * `Span<T>` можно получить от массива, стековой памяти (`stackalloc`), unmanaged memory (через `MemoryMarshal`).
  * `ref struct` — нельзя хранить в куче, нельзя возвращать как `object`, нельзя использовать в async/iterator.
* **Memory<T>** — похожа на `Span<T>`, но хранится в куче (полезно для асинхронного кода).
* **SafeHandle** — управление нативными дескрипторами вместо сырых `IntPtr`.
* **Marshal** и `System.Buffers.ArrayPool<T>` — для эффективного повторного использования буферов.

Пример stackalloc + Span:

```csharp
Span<byte> buffer = stackalloc byte[256];
FileStream fs = ...;
int read = fs.Read(buffer); // не копируем в managed heap
```

# Часть 7. Примеры кода (полезные шаблоны)

### 7.1 Пример: `ref` параметр

```csharp
void Swap(ref int a, ref int b)
{
    int t = a;
    a = b;
    b = t;
}

int x = 1, y = 2;
Swap(ref x, ref y); // x==2, y==1
```

### 7.2 `ref` return — обращение к элементу массива

(см. выше в разделе 4.3)

### 7.3 Unsafe пример с массивом

```csharp
unsafe
{
    int[] arr = { 10, 20, 30 };
    fixed (int* p = arr)
    {
        for (int i = 0; i < arr.Length; i++)
        {
            Console.WriteLine(*(p + i)); // перебор через указатель
        }
    }
}
```

### 7.4 Stackalloc + Span

```csharp
void Process()
{
    Span<int> temp = stackalloc int[64];
    // работа с temp — быстро и без аллокаций в куче
}
```

### 7.5 Pinning через GCHandle

```csharp
byte[] data = new byte[1024];
var handle = GCHandle.Alloc(data, GCHandleType.Pinned);
try
{
    IntPtr addr = handle.AddrOfPinnedObject();
    // вызвать нативную функцию, передав addr
}
finally
{
    handle.Free();
}
```

# Часть 8. Практические советы и типичные ошибки

### 8.1 Что лучше использовать

* Если можно — используйте **управляемые** структуры (`Span<T>`, `Memory<T>`, `ArrayPool<T>`, `SafeHandle`) вместо `unsafe`.
* `unsafe` нужен для interop и редких случаев экстремальной оптимизации.

### 8.2 Типичные ошибки

* **Закрепление (pinning)** на длительный срок — препятствует компактации и вызывает фрагментацию.
* **Потеря ссылок** (в managed) — «утечка» по смыслу: объекты остаются живыми в куче из-за статических коллекций, подписок на события и т.п.
* **Неправильное освобождение нативной памяти** (`Marshal.FreeHGlobal` забыли) — утечки нативной памяти.
* **Использование указателя на освобождённую/перемещённую память** — UB в `unsafe`.
* **Боксинг/анбоксинг** в горячем цикле — потеря производительности.

### 8.3 Отладка утечек памяти

* Проверять корни (roots) — откуда объекты остаются достижимыми.
* Использовать профайлеры памяти (.NET Memory Profiler, dotMemory, PerfView).
* Проверять ненужные подписки на события, статические коллекции, кеши.

# Часть 9. Контроль ресурсов: IDisposable и финализаторы

* Для неуправляемых ресурсов (файлы, сокеты, нативная память) используйте `IDisposable` и `using`.
* `finalize` (деструктор) — ненадёжный и выполняется с задержкой; используйте только как запасной механизм.
* Шаблон `Dispose` + SafeHandle для корректной очистки.

Пример:

```csharp
class MyResource : IDisposable
{
    private IntPtr nativeHandle;
    private bool disposed;

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (!disposed)
        {
            // освободить nativeHandle
            disposed = true;
        }
    }

    ~MyResource()
    {
        Dispose(false);
    }
}
```

# Часть 10. Заключение — ключевые мысли

* Оперативная память — сложная система: иерархия (кэш → RAM → диск), виртуализация, страницы. Понимание этого помогает писать производительный код.
* В C# **ссылки** (reference types) и **значимые типы** (value types) — фундамент, который влияет на производительность, семантику и поведение GC.
* **Сборщик мусора** упрощает управление памятью, но не отменяет необходимость думать о жизненном цикле объектов, утечках ссылок и закреплениях.
* **Указатели (`unsafe`)** дают мощь и риск — используйте их осознанно. Чаще предпочтительнее `Span<T>` / `Memory<T>` / `SafeHandle`.
* Для безопасного и быстрого кода: минимизируйте копирования, избегайте ненужного бокса, используйте `ref`/`in`/`ref returns`, `stackalloc` и `ArrayPool` при необходимости.
